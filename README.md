For this project I decided to work on the social app Discord and create a bot that handles and secures the exchanges.
For the encryption, I chose ECC as it provides equivalent security to RSA with smaller key sizes (256-bit ECC ≈ 3072-bit RSA), faster operations, and is used in modern systems like Signal and TLS.

The project contains 3 files :

- ca.py is the Certificate Authority, it contains the script that creates and signs certificates for users.
  It generates EC key pairs and X.509 certificates for each user, signs them with the CA private key, and stores them on disk.

- crypto.py is the file that handles the encryption process.
  It uses ECIES for data encryption.
  ECIES is a two layer encryption structure that functions using a first AES key that encrypts the message once for everyone, and a second separate ECDH-derived key that wraps the first AES key for every recipient.
  The following protocols are used in that order for the encryption process : 
    - AES - GCM : encrypts & creates an authentication tag, so if the ciphertext is modified, decryption fails and returns an error message.
      GCM also requires a 12 byte nonce so the result of that first step is : key + nonce + text &rarr; cipher text + its authentication tag
    - ECDH : a, aP, b, bP are the two parties' keys computed using Elliptical Curves.
      aP and bP are publicly shared, and by mutiplying the other person's public key with our own private key, we get a shared secret abP = baP that can only be obtained by someone who knows either a or b.
    - HKDF : abP previously generated has a mathematical structure and follows a specific distribution, which is not great in terms of safety since it follows a pattern.
    - To solve that problem, we use HDKF to produce a uniformly random key. 
        1. "mix" abP with HMAC (one way hash function, which means it can't be applied "the other way" to find abP)
        2. expand the obtained value using HMAC repeatedly until we reach a 32 bytes long key 
  The ECDH and HKDF steps result in an AES looking key (k) that will be used to wrap the first AES key.
  The advantage is that k does not need to be shared as it can only be reconstructed by the parties that own the EC private keys a and b.
    -> two people find the same secret key without needing to share it, that solves one of the biggest problems in data security and encryption processes.

- bot.py is the script for the bot. \
  *BOT TOKEN AND CHANNEL ID NEED TO BE MANUALLY INSERTED IN THE CODE* \
  The bot is the link between the encryption system and the discord users, it responds to the following commands :
    * !auth \<member1\> \<member2\> ... 
        "authorize" : adds members to secure group, the command !auth alone adds the user to its own secure group
    * !noauth \<member1\> \<member2\> ...
        "not authorized" : removes members from secure group
    * !post \<msg\>
        msg is deleted and its ciphertext posted to the channel
    * !read
        dms the plaintext of the last message posted if in authorized group, if sent as reply to another message, decrypts the message replied to
    * !members
        shows current authorized group
      
  The only purpose of the roles is to visualize the secure group, but the authentification is done through the dictionaries that are generated by crypto.py, not the roles.
  Even if someone bypassed Discord's permissions, they still couldn't decrypt the message without their key entry.
  When the bot starts running, it checks if there are new members that don't have a certificate yet, if so, it creates the certificate and the secure group associated to the member.
  Similarly, it searches for people who left while the bot was offline, if there any, it deletes the associated certificate, role and group from groups.json.
